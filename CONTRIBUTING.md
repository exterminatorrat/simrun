# Contributing to SimRun

Thanks for helping. SimRun is a small, dependency-light TypeScript app; the goal is to keep it honest, local-first and easy to audit. Try it first at [simrun.vercel.app](https://simrun.vercel.app).

## Setup

Requires Node.js 20+ (CI uses 22) and npm.

```sh
git clone https://github.com/exterminatorrat/simrun.git
cd simrun
npm ci
npm run dev -- --host 127.0.0.1 --port 5173
```

## Before you open a pull request

```sh
npm run typecheck
npm test
```

`npm test` builds `dist/` and runs `node --test tests/*.test.mjs`. For UI changes also run the browser checks with mocked providers:

```sh
python -m pip install -r tests/requirements.txt
python -m playwright install chromium
python tests/browser.py --url http://127.0.0.1:5173
```

CI ([verify.yml](.github/workflows/verify.yml)) runs the same steps on `main` and on manual dispatch.

## Project principles

- **Honesty over polish.** Never fake routes, seeded activities or successful routing. Simulated data must stay labeled as simulated.
- **Local-first.** No accounts, analytics, backend or secrets. Keep user data in the browser.
- **Minimal dependencies.** TypeScript is the only build dependency. Do not add runtime dependencies without discussion.
- **Strict TypeScript, native DOM, ES modules.** No framework.
- **Deterministic simulation.** Same seed and settings must yield the same output.
- **Respect providers.** Keep throttling, caching and the Nominatim opt-in. Do not add traffic to public services in tests; use mocks.

## Pull requests

- Branch from `main`; one focused change per PR.
- Add or update tests in `tests/` when behavior changes.
- Update the README or `docs/` if behavior, setup or limits change.
- Do not commit `dist/`, `node_modules/`, `.vercel/`, `.env*` or generated archives.
- Describe what changed, why, and how you verified it, including anything you could not verify.

Commit messages should be short and imperative (for example `Fix loop planner closing gap`).

## Vendored and third-party files

`public/vendor/` is generated by `npm run vendor`; do not hand-edit it. Keep upstream license notices and update [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md) when adding anything third-party.

## Reporting issues

Use GitHub Issues for bugs and feature requests, and include browser, OS and steps to reproduce. For security problems, follow [SECURITY.md](SECURITY.md) instead.

## Versioning and releases

Record user-visible changes under `[Unreleased]` in `CHANGELOG.md`. Before a release, move those entries into a dated version section and update `package.json`. Before 1.0.0, use `0.MINOR.PATCH`: increment PATCH for compatible fixes and MINOR for new features or breaking changes. After 1.0.0, follow Semantic Versioning for breaking changes, compatible features, and fixes. Keep the package version unchanged during ordinary feature work.
